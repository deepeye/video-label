# 视频语料标注平台 · 演示 Demo PRD

> 文档版本：v2.0-demo / 2026-06-18 变更说明：本版本将原 v1.0 生产 PRD 收敛为**客户演示 Demo**。所有数据 Mock，无真实后端处理。 受众：产品/销售 + 实现该 Demo 的 AI 编程助手

------

## 第一章：产品概述

**一句话定位：**

> 本 Demo 是一套**纯前端的视频标注流程演示系统**，让**销售与产品在客户现场**能够**完整走通「上传→元信息→自动标注→人工审核→导出」五步叙事**，而无需**搭建任何后端、GPU 或真实模型推理环境**。

核心判断：Demo 的成功标准不是「技术真实」，而是「**叙事可信 + 现场零故障 + 可反复重置**」。因此一切围绕「**看起来在处理、实际读 Mock**」设计，唯一需要真实交互的是「人工审核纠正」这一步——因为那是最能打动客户的「人机协同」卖点，必须真的能点、能改。

### 1.1 与「真实产品/普通 PPT」的差异化对比

Demo 的竞品其实是「静态 PPT/录屏」。对比：

| 维度             | 静态 PPT / 录屏 | 本 Demo                                | 实现方式                         |
| ---------------- | --------------- | -------------------------------------- | -------------------------------- |
| 客户可亲手操作   | 否              | 是，审核环节客户可亲自接受/改框        | 内存状态真交互，详见 3.4         |
| 流程连贯性       | 切页跳跃        | 一个数据贯穿五步，前一步产出喂给后一步 | 单一 Mock 数据集贯穿全流程       |
| 现场可控性       | 录屏固定        | 可暂停讲解、可重置重来、可跳步         | Demo 控制条 + 一键重置，详见 4.1 |
| 「自动标注」观感 | 截图            | 进度条→框逐个浮现的动画                | 定时器驱动的揭示动画，详见 3.3   |
| 导出真实性       | 假截图          | 真生成可下载的 JSON/ZIP                | 浏览器内打包，详见第八章         |

不列入：真实推理、真实转码、真实账户体系——Demo 明确不做。

### 1.2 三类「演示场景」（替代用户画像）

Demo 面向的是「演示场合」，画像调整为场景：

**场景 A：销售主讲，客户旁观**

- 目标：5 分钟内讲完全流程，节奏可控不卡壳。
- 最大风险：现场加载慢、动画卡、数据没复位导致「穿帮」。
- 关键功能：**Demo 控制条**（开始/暂停/下一步/重置），让主讲掌控节奏。

**场景 B：客户上手试用**

- 目标：让客户亲手在审核环节点「接受/否决/改框」，建立参与感。
- 最大风险：客户点出预期外的状态导致界面异常。
- 关键功能：**审核环节真交互 + 防呆**（只开放安全操作，其余禁用置灰）。

**场景 C：技术评估方旁听**

- 目标：让对方相信「这背后是有数据模型和导出能力的真东西」。
- 最大风险：导出是假的、数据结构经不起看。
- 关键功能：**真实导出文件**，结构对齐生产 schema（第五章/第八章）。

### 1.3 可行性边界

| 在范围内（及原因）                     | 明确排除在外（及原因）                                  |
| -------------------------------------- | ------------------------------------------------------- |
| 上传交互（接受文件拖入的动作）         | 真实上传/分片/断点续传——Demo 不需要真传文件到任何服务器 |
| 元信息「提取」动画 + 预制元信息展示    | 真实 ffprobe 解析——读 Mock JSON 即可                    |
| 自动标注「推理」进度 + 预制标注揭示    | 真实模型推理/GPU——纯前端定时器模拟                      |
| 人工审核真交互（接受/否决/改框/补框）  | 多级盲审/仲裁——Demo 只演单审                            |
| 真实导出可下载文件（JSON/ZIP）         | 真实训练管线回流——只导出，不回流                        |
| 2~3 个预置 Demo 视频（短片，本地打包） | 用户任意视频的真实标注——上传任意文件时回退到预置脚本    |
| 一键重置、Demo 控制条                  | 账户/权限/多人协作——Demo 无登录                         |

诚实的边界：**上传任意视频时，系统并不真的处理它**，而是用预置 Mock 流程演示。需在 Demo 中以友好方式处理（详见 3.1 待决问题）——倾向「上传任意文件后，自动套用预置的城市道路 Demo 数据继续流程」。

## 第二章：整体布局与导航

Demo 在生产三栏布局基础上，**增加一条贯穿顶部的「流程步骤条」和一条「Demo 控制条」**，让客户始终知道「现在第几步、整体几步」。

```
+----------------------------------------------------------------------+
|  顶栏  [Frameworks Demo]      ① 上传 → ② 元信息 → ③ 自动标注 → ④ 审核 → ⑤ 导出 |  <- 流程步骤条(高亮当前)
+----------------------------------------------------------------------+
|  Demo控制条:  [▶ 自动演示] [⏸暂停] [⏭下一步] [↺ 重置Demo]   速度[1x▾] |  <- 仅Demo有
+--------+----------------------------------------------+--------------+
| 左导航  |  中央工作台 (随当前步骤切换内容)              | 右属性面板    |
| (步骤)  |                                              |              |
| ①上传   |   [当前步骤的主视图]                          | 当前步骤说明  |
| ②元信息 |                                              | 与上下文操作  |
| ③标注   |                                              |              |
| ④审核   |                                              |              |
| ⑤导出   |                                              |              |
+--------+----------------------------------------------+--------------+
|  状态栏  Demo数据: 城市道路样例 | 已Mock | 步骤 3/5                    |
+----------------------------------------------------------------------+
```

**布局逻辑说明：** 生产版本左导航是「功能模块」，Demo 改成「**流程步骤①~⑤**」，因为 Demo 的灵魂是「线性叙事」而非「功能罗列」。顶部步骤条让客户一眼看到「这是一个有头有尾的完整流程」，消除「是不是只演了一个功能」的疑虑。Demo 控制条是 Demo 独有的，把演示节奏的控制权交给主讲，是现场不翻车的关键。

## 第四章：超越「普通 Demo」的差异化设计

Demo 的差异化不再是「超越竞品产品」，而是「**比普通录屏/PPT 更可信、更可控**」。

### 4.1 Demo 控制条与一键重置（防翻车的核心）

**第一段 — 为何普通 Demo 没有：** 普通录屏是线性固定的，无法暂停讲解、无法应客户要求重看某步；而真实产品 Demo 又常因「上一场没复位、数据脏了」当场穿帮。两者都缺一个「演示编排层」——因为它对真实产品毫无价值，只对「演示」这个特定场景有价值，所以没人为生产系统做。

**第二段 — 本 Demo 如何实现：** 做一个独立于业务的 **Demo 编排状态机**：`idle→step1→…→step5→done`，控制条提供「自动演示（按预设时长自动推进）/ 暂停 / 手动下一步 / 重置」。重置时**把内存里的 Demo 状态深拷贝回初始 Mock 快照**，保证每场从干净状态开始。推荐用单一全局 store（Zustand）持有 `demoStep` 与 `datasetSnapshot`，重置即 `set(initialSnapshot)`，O(1) 且无残留。

**第三段 — 交互流程：**

```
主讲点[▶自动演示]
    |
    v
状态机按预设时长自动 step1->2->3 (元信息/标注揭示动画自动播)
    |
    +-- 客户提问 --> 主讲点[⏸暂停] -> 当前画面冻结讲解
    |
    +-- 想重看 --> [↺重置] -> 深拷贝初始快照 -> 回step1
    |
    v
到step4(审核) 自动模式暂停, 交给客户手动操作
```

**第四段 — 风险与应对：** 风险：自动演示时长与主讲讲话节奏不同步，画面跑太快。应对：提供 1x/2x/即时 速度档 + 随时可暂停；审核步骤强制停在手动，不自动跳过（最需要互动的环节不抢客户的操作）。备选：若现场网络/设备差，提供「纯手动」模式，每步都靠主讲点「下一步」。

### 4.2 真实可下载导出（让技术评估方信服）

**第一段 — 为何普通 Demo 没有：** PPT/录屏里的「导出」只能是截图，因为它背后没有真实数据结构。要导出真文件，前提是 Demo 内存里得有一份结构良好、且能反映用户操作的数据——多数演示图省事不做这层。

**第二段 — 本 Demo 如何实现：** Mock 数据从一开始就**严格按生产 schema 组织**（第五章），人工审核真实修改这份内存数据，导出时用 JSZip 在浏览器内打包成 zip 下载。推荐导出「原生 JSON（含 review/source 溯源）」作为默认格式，因为它最能展示「人机协同的可追溯性」这一卖点，让技术方看到数据是真的、改动是留痕的。

**第三段 — 交互流程：**

```
客户在step4把"行人0.41"接受、把"车辆0.48"改了框
    |
    v
step5预览JSON -> 行人source仍machine+accepted, 车辆source转human+corrected
    |
    v
下载zip -> 客户用文本编辑器打开 -> 看到自己刚才的操作被真实记录
```

**第四段 — 风险与应对：** 风险：客户打开 zip 发现帧图是占位图/数量对不上而起疑。应对：导出包内放真实的几张样例帧缩略图 + 完整标注 JSON，manifest 注明「演示数据集」；不宣称是完整训练集。备选：若不希望暴露文件细节，仅导出单个 JSON 而非整包。

## 第六章：技术架构

Demo 是**纯前端单页应用，零后端**。

```
+-------------------------------------------------------------+
| 浏览器单页应用 (SPA)  职责: 全流程演示, 无网络依赖           |
|  +-------------------+  +-------------------+               |
|  | Demo编排状态机     |  | 业务视图(5步骤)   |               |
|  | demoStep/速度/重置 |  | 上传/元信息/标注/ |               |
|  +-------------------+  | 审核/导出         |               |
|  +-------------------+  +-------------------+               |
|  | 画布与时间轴       |  | 揭示动画引擎       |               |
|  | (Konva 框/控制点)  |  | (定时器驱动)      |               |
|  +-------------------+  +-------------------+               |
+-----------------------------↓-------------------------------+
| 本地静态资源 (随应用打包, 无服务端)                          |
|  Mock数据集JSON │ 样例视频mp4 │ 样例帧缩略图                |
+-------------------------------------------------------------+
```

依赖库表：

| 库名            | 用途                   | 为何优于替代方案                                       | 大致包体积  |
| --------------- | ---------------------- | ------------------------------------------------------ | ----------- |
| React 18 + Vite | SPA 框架与构建         | Vite 冷启快、打包出纯静态文件，便于现场拷贝/离线运行   | ~45KB gzip  |
| Konva.js        | 画布框/控制点拖拽      | 审核改框需要现成的可拖拽控制点，裸 Canvas 自实现成本高 | ~120KB gzip |
| Zustand         | Demo 编排+标注内存状态 | 重置=一次 set，深拷贝快照简单；比 Redux 轻             | ~3KB gzip   |
| JSZip           | 浏览器内打包导出 zip   | 纯前端生成可下载包，无需后端，事实标准                 | ~95KB gzip  |
| FileSaver.js    | 触发浏览器下载         | 跨浏览器下载兼容性好，比手写 a[download] 稳            | ~3KB gzip   |

**最大架构风险说明：** 最大风险是**现场环境的离线/网络不确定性**：客户现场可能没网、或 CDN 被墙。应对：**全部资源（含视频、字体、库）本地打包，构建为可双击打开或本地静态服务运行的纯静态产物，零外部网络请求**。这样无论现场有没有网都能跑。次要风险是不同笔记本浏览器版本差异——锁定主流 Chrome/Edge 最近两个版本，演示前在目标机器上预跑一次。

## 第九章：开发优先级

Demo 的优先级标准是「**对现场演示效果的影响**」。

**P0 — 没有这个，Demo 根本演不了** 五步骤线性流程跑通（上传→元信息→标注揭示→审核真交互→导出真下载）、1 个城市道路样例的完整 Mock 数据、Demo 控制条的「下一步」与「重置」。 *交付标准：能从头到尾走完一遍不报错。*

**P1 — 没有这个，客户看完无感** 自动标注的「框逐个浮现」揭示动画、元信息打字机揭示、审核步骤的接受/否决/改框真交互与队列、导出真生成 zip。 *交付标准：流程有「在处理」的观感，审核能真互动。*

**P2 — 有了这个，客户会觉得「这东西成熟」** Demo 控制条完整（自动演示/暂停/速度档）、3 个样例可切换、撤销（Ctrl+Z）、防呆提示。 *交付标准：现场可控、不翻车、可反复演示。*

**P3 — 有了这个，加分但非必须** 多导出格式切换、键盘快捷键、离线纯静态打包、暗色主题/品牌化外观。 *交付标准：精致，锦上添花。*

层级按「演示效果」排：审核真交互虽实现稍重，仍放 P0/P1，因为它是唯一让客户「亲手参与」的环节，是 Demo 的情绪高点。

## 第十章：性能指标

Demo 的指标关注「**现场流畅与可信**」，仍为具体数字。

| 指标                       | 目标值  | 测量方法                          | 劣化阈值                  |
| -------------------------- | ------- | --------------------------------- | ------------------------- |
| 首屏加载（本地静态）       | ≤ 2s    | 从打开页面到步骤①可交互，前端埋点 | > 5s（客户开场等待尴尬）  |
| 步骤切换响应               | ≤ 100ms | 点「下一步」到新视图渲染          | > 300ms                   |
| 审核改框拖拽帧率           | ≥ 50fps | Chrome Performance 录制拖框 5s    | < 30fps（拖动卡顿）       |
| 揭示动画帧率               | ≥ 50fps | 录制标注浮现动画                  | < 30fps（动画掉帧显廉价） |
| 导出打包耗时               | ≤ 1.5s  | 点下载到文件生成                  | > 5s（客户以为卡死）      |
| 重置耗时                   | ≤ 200ms | 点重置到回步骤①                   | > 1s                      |
| 应用打包体积（含样例视频） | ≤ 30MB  | 构建产物总大小                    | > 80MB（拷贝/加载慢）     |
| 切帧 seek（30s 短视频）    | ≤ 100ms | 按帧导航到画面更新                | > 250ms                   |

劣化阈值用于排期：首屏加载与揭示动画帧率直接决定客户第一印象，触及劣化阈值按 P0 缺陷处理。

## 第十一章：开发者交接说明

本章直接写给将实现本 Demo 的你（AI 编程助手）。

**a) 实现顺序建议** 先建 **Mock 数据集（城市道路样例的完整 JSON）+ Demo 编排状态机（demoStep 与重置）**，因为这两者是 Demo 的骨架，定下来后五个步骤视图只是消费它。接着做**步骤④审核工作台**——它是唯一的真交互、技术最重、也是 Demo 高点，先把它做扎实（Konva 画布 + 接受/否决/改框 + 内存状态更新）。然后做**步骤⑤导出**，因为它消费审核后的内存状态，做完即可验证「客户改动→导出留痕」这条核心链路真的通。最后补**步骤①②③的揭示动画**——它们是「观感」，逻辑最简单，放最后用定时器读 Mock 渲染即可。控制条与重置贯穿始终，尽早接上。

**b) 最可能导致返工的三个决策**

1. **审核改动存哪**。安全默认：存在 Zustand 内存 store 的标注副本里，导出直接读它。改变信号：若你把改动只画在 Konva 图层而没回写 store，导出会拿不到客户的改动——务必「改框即回写数据」。
2. **重置如何彻底**。安全默认：保存一份初始 Mock 的深拷贝快照，重置时整体替换 store。改变信号：若重置后仍残留上一场的框/审核状态，说明你改的是引用而非深拷贝，必须深拷贝快照。
3. **Mock schema 要不要对齐生产**。安全默认：对齐（第五章），review 用单对象。改变信号：若产品说「Demo 后要接真后端」，你现在偷懒简化 schema，接后端时导出格式会全改——按第五章对齐能避免。

**c) 哪里要严格，哪里可以灵活**

| 章节                   | 性质     | 说明                                           |
| ---------------------- | -------- | ---------------------------------------------- |
| 第五章 数据模型        | **约束** | schema 对齐生产，导出结构不得随意简化          |
| 第三章步骤④审核交互    | **约束** | 接受/否决/改框必须真改内存数据，这是 Demo 灵魂 |
| 第四章 4.1 重置/控制条 | **约束** | 必须能干净重置，现场反复演示依赖它             |
| 第六章「纯前端零后端」 | **约束** | 不得引入任何真实后端/外部网络依赖              |
| 揭示动画的时长与样式   | **建议** | 默认值见 demo_script，可调                     |
| 第二章 布局像素        | **建议** | 步骤条+控制条结构保留，尺寸可调                |
| 第七章 快捷键          | **建议** | 可裁剪，A/D 接受否决建议保留                   |

**d) 已知的未知项**

- **客户拖入自有视频的「真画面 + 假框」一致性**未解决（见 3.1）。建议 Demo 默认引导用预置样例，若产品坚持允许任意上传，需现场话术配合「标注为样例演示数据」，文档此处不完整。
- **样例视频从哪来、版权是否可商用展示**未在本 PRD 解决。你需要确认拿到可对外演示的无版权风险短视频素材，否则现场播放有风险。
- **目标演示设备/浏览器**未锁定。离线纯静态打包（P3）是否必须，取决于现场是否有网——建议向销售确认演示环境后再决定是否投入离线打包。
- **样例数量与场景**：本 PRD 假设「城市道路」为主样例。若客户行业不同（如医疗、零售），现有 Mock 不贴合，需要按客户行业另制样例数据——这是上线前要和销售对齐的内容缺口。
